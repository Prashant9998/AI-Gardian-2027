1. Introduction

1.1 Purpose

This Software Requirements Specification (SRS) defines, in engineering-grade and audit-ready detail, the complete functional and non-functional requirements for AI Cyber Guardian — an autonomous, multi-tenant SaaS platform that detects, classifies, and neutralises web-application cyber-attacks in real time. It is the authoritative, change-controlled contract between business stakeholders and the delivery organisation, and the basis for design, implementation, verification, deployment, and compliance attestation.

This document is written to be conformant with ISO/IEC/IEEE 29148:2018 (Requirements Engineering) and IEEE Std 830-1998. Every requirement is uniquely identified, prioritised, verifiable, and traceable (see §14). The intended audiences are: the engineering and QA organisation, security and compliance functions, platform operations (SRE), product management, procurement/security reviewers of prospective enterprise customers, and future maintainers.

1.2 Scope

AI Cyber Guardian is a cloud-native, API-first security service that operates as a decision plane alongside a customer's web infrastructure. A lightweight backend SDK (or a direct REST call) forwards request metadata only to the Guardian control plane, which returns an enforcement decision — ALLOW, BLOCK, or HONEYPOT — within the contracted latency budget. Live customer traffic is never proxied through Guardian; the platform augments, and never replaces, existing infrastructure.

In scope for this release baseline:

  • Two-stage ingress filter: stateless rate limiting / list enforcement, followed by rule-engine + ML deep analysis.
  • Supervised and unsupervised ML threat models (Random Forest classifier, Isolation Forest anomaly detector) with a governed MLOps lifecycle.
  • A deterministic rule engine covering the core OWASP attack categories.
  • An autonomous defence engine (IP block, account lock, session termination, honeypot activation) with full reversibility and audit.
  • A transparent honeypot returning 200 OK deception content and building persistent attacker intelligence.
  • Multi-tenant management plane with RBAC/ABAC, enterprise SSO (SAML 2.0 / OIDC), SCIM 2.0 user provisioning, and org/site hierarchy.
  • Real-time dashboards, scheduled reporting, and exportable evidence (PDF/CSV/JSON).
  • Enterprise integrations: outbound webhooks, SIEM streaming (CEF/LEEF/JSON), SOAR/ticketing, and ChatOps.
  • Tamper-evident audit logging, data-governance controls, and compliance evidence generation.

Out of scope (this baseline): full inline reverse-proxy/CDN data-plane enforcement; on-device agent for non-HTTP protocols; managed SOC / human-in-the-loop response service; DDoS scrubbing at the network layer (L3/L4). These are candidate roadmap items and are explicitly excluded from acceptance.

2. Overall Description

2.1 Product Perspective

AI Cyber Guardian is a standalone, cloud-native SaaS that acts as an out-of-band security decision service. It sits logically between a site's visitors and the customer's backend, invoked by the client-side SDK. Only request metadata (IP, headers, path, method, body sample, cookies, query parameters) is transmitted to the control plane; the live request/response never traverses Guardian infrastructure. Enforcement is executed by the SDK at the customer edge based on the returned decision. This out-of-band model bounds Guardian's blast radius, eliminates it as a single point of failure for customer availability (fail-open by policy), and simplifies the customer's data-flow and compliance posture.

2.5 Design & Implementation Constraints

  • Out-of-band only: the platform MUST NOT proxy live customer traffic — metadata only.
  • Fail-open by policy: if the control plane is unreachable, the SDK MUST default to ALLOW (configurable to fail-closed per route) so Guardian never causes a customer outage.
  • Honeypot fidelity: deception content MUST be returned as 200 OK; a 301/302 redirect is strictly prohibited.
  • Latency budget: synchronous decision path MUST complete within the SLO (§4.1); ML inference MUST run on CPU (no GPU dependency) within its budget.
  • Licensing hygiene: only permissive licences (MIT/BSD/Apache-2.0). No copyleft (GPL/AGPL) in distributed artefacts. An SBOM (SPDX/CycloneDX) MUST be produced per release.
  • Data minimisation: raw request bodies retained ≤ 24 h by default (tenant-configurable within policy bounds), then hashed or deleted; no plaintext secrets/PII persisted.
  • Statelessness: decision services MUST be horizontally scalable and stateless; all shared state lives in Redis/PostgreSQL.

2.6 Assumptions & Dependencies

  • Customers can install a backend SDK or invoke the REST API from their server tier.
  • A geolocation provider is available; results are cached (24 h TTL) to respect provider limits and reduce cost.
  • The certification training corpus (CSIC 2010 + governed supplemental data) is licensed for the intended use.
  • Enterprise customers can federate identity via SAML/OIDC and (optionally) SCIM.
  • Managed cloud primitives (KMS, object storage, managed Postgres/Redis, load balancers) are available in target regions.

2.7 Multi-Tenancy & Isolation Model

The platform is a logically-isolated, pooled multi-tenant system with an optional siloed tier for regulated customers:

LayerIsolation Mechanism
IdentityEvery principal, key, and record is scoped to a tenant_id; all queries are tenant-filtered and enforced at the API/authorization layer (defence-in-depth with row-level security in PostgreSQL).
DataPooled schema with mandatory tenant predicate; honeypot data resides in a separate schema with no foreign keys to real tenant data. Enterprise/regulated tier MAY use a dedicated database/schema.
ComputeShared stateless workers; per-tenant rate limits and quotas prevent noisy-neighbour effects. Enterprise tier MAY use dedicated node pools.
EncryptionPer-tenant data-encryption keys wrapped by a KMS master key (envelope encryption); optional customer-managed keys (BYOK) for the enterprise tier.
ResidencyTenant data pinned to a chosen region; cross-region movement only for DR to a same-jurisdiction secondary.

6.2 Deployment Architecture

Kubernetes across ≥ 3 AZs in the primary region, provisioned by Terraform and deployed via GitOps. Stateless decision services scale horizontally behind the gateway; managed PostgreSQL (primary + sync replica + read replicas, PITR) and Redis Cluster provide state. A warm secondary region holds continuously-replicated data for DR (RPO ≤ 5 min / RTO ≤ 1 h). Environments are fully isolated: dev, staging, production (see §11).

6.3 End-to-End Request Processing Flow

#StepLatency Target
1Visitor request hits the customer's server; SDK intercepts and extracts metadata.~2 ms
2SDK calls Decision API (POST /v1/check) over TLS.~5 ms (network)
3Stage 1 — rate check, allow/block lists, scanner UA check.< 1 ms
4Stage 2 — rule engine evaluates core rules.~50 ms
5Stage 2 — Isolation Forest anomaly score.~100 ms
6Stage 2 — Random Forest classification.~100 ms
7Decision engine fuses scores → level + action + explainability.~20 ms
8If CRITICAL: honeypot content rendered.~30 ms
9API returns decision to SDK; SDK enforces (pass / deny / 200 OK honeypot).~7 ms
10Event published to async pipeline; persisted; dashboards updated.Non-blocking, < 2 s to UI

Persistence and dashboard fan-out (step 10) are asynchronous — the decision is returned before writes complete, so logging never inflates the customer's request latency.
