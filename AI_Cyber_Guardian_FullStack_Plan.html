3. The Chronological 8-Step Master Implementation Plan

To achieve an enterprise-ready system, development must proceed in the strict sequential order below. Each step builds the direct technical prerequisite for the next.

1 Real-Time WebSocket Streaming Pipeline
HIGHEST PRIORITY

Rationale: The frontend currently polls or uses local simulation. Connecting live WebSockets ensures sub-100ms attack alerts during demonstrations, giving immediate visual impact.

Technical Tasks:

  • FastAPI WebSocket Server: Create guardian-control-plane/api/routers/ws.py exposing /api/v1/ws/threats. Implement a thread-safe ConnectionManager to broadcast security events to multiple connected SOC operators simultaneously.
  • Event Interceptor Hook: Wire evaluate_decision() and honeypot/engine.py to fire asynchronous WebSocket payload broadcasts whenever a score > 30 is computed or a honeypot canary is tripped.
  • React Custom Hook: Implement cyberprep-app/src/hooks/useThreatStream.js with auto-reconnect, exponential backoff, and state merging directly into the Live Threat Feed.
  • Visual & Auditory Alerts: Add row pulse animation and optional alert chime for CRITICAL severity events.

Acceptance Criteria: Triggering a curl request with an SQL injection payload immediately displays the attack event on the React dashboard in < 100ms without page refresh.

2 Real ML Dataset Training & Model Serialization
STATISTICAL RIGOR

Rationale: The ML engine currently uses synthetic data. Training on real HTTP attack datasets (CSIC 2010 and CIC-IDS2017) provides genuine scientific validity for university viva, conference publications, and production detection.

Technical Tasks:

  • Data Preprocessing Pipeline: Create guardian-control-plane/ml/preprocess.py to parse HTTP requests, extract headers, query params, and body strings from the CSIC 2010 dataset.
  • Feature Engineering: Extract request length, entropy, special symbol ratios (', ", <, >, ;, --, \, /), parameter count, and TF-IDF n-grams (1–3 chars).
  • Model Training: Train an Isolation Forest (contamination=0.05) for zero-day anomaly detection and a Random Forest Classifier (100 estimators) for multi-class categorization.
  • Model Artifact Serialization: Serialize trained weights into isolation_forest.joblib, random_forest.joblib, and vectorizer.joblib. Load models during FastAPI lifespan startup in < 500ms.

Acceptance Criteria: Model achieves ≥ 92% F1-score and ≤ 4.5% False Positive Rate on clean test traffic, backed by confusion matrix benchmarks.

3 Protected Target Application Lab ("Protected App Lab")
FUNCTIONAL VALIDATION

Rationale: A security tool cannot be evaluated in isolation. Building a realistic target application (e.g. an E-commerce store or Student Portal) demonstrates the Guardian SDK actively defending a live business application.

Technical Tasks:

  • Build Target Web App: Create sample-target-app/ with realistic endpoints:
    • POST /api/auth/login (User authentication with brute force vulnerability)
    • GET /api/catalog/search?q= (Product search vulnerable to SQL injection)
    • POST /api/reviews (Customer feedback vulnerable to stored XSS)
    • GET /api/files/view?doc= (Document viewer vulnerable to path traversal)
  • SDK Integration: Attach Guardian middleware in 3 lines: 
    app.use(guardianMiddleware({ siteId: "shop-prod-01", controlPlane: "http://localhost:8000" }));
  • Behavioral Verification:
    • Legitimate traffic passes untouched (HTTP 200).
    • High-severity attacks receive an immediate security shield (HTTP 403).
    • Critical attackers accessing fake /admin or /.env are seamlessly diverted into the Honeypot without touching the target application's real database.

Acceptance Criteria: Live attacks against the sample app are intercepted transparently with zero disruption to benign users.

4 1-Click Interactive Attack Demo Harness
KEY PRESENTATION ASSET

Rationale: In a live project evaluation, manually typing curl commands is slow and prone to typos. An automated multi-stage attack harness demonstrates Red Team vs. Blue Team mechanics dynamically in 30 seconds.

Technical Tasks:

  • Multi-Stage Attack Script: Create simulate_demo_scenario.py executing 4 distinct threat vectors in timed intervals:
    • Stage A (0–5s): Reconnaissance scan sending scanner User-Agents (sqlmap, nikto).
    • Stage B (5–12s): Credential Brute Force with 15 rapid failed logins to trip Rule R4 rate limiting.

  • Dashboard Trigger Button: Add an interactive "▶ Run Live Attack Demo" button on the Dashboard Topbar that triggers the scenario and highlights corresponding dashboard panels sequentially.

Acceptance Criteria: Evaluators can click one button and watch the entire security lifecycle (detect, block, trap, report) unfold autonomously on screen.

4. Threat Decision Matrix & Response Protocols

The decision engine fuses deterministic signatures with machine learning probabilities to classify incoming requests into four actionable response tiers:

Score Band Severity Detection Signatures / Triggers Autonomous Response Action Telemetry Logged
0 – 29 LOW Normal user browsing, valid form submissions, static assets, score < 30. Pass through untouched. Minimal audit log recorded. Timestamp, IP hash, path, latency.
30 – 59 MEDIUM Scanner user-agents (nikto, dirbuster), minor anomalies, parameter fuzzing. Pass through + Flag Session. Email notification dispatched if enabled. Full headers, query params, tool fingerprint.
60 – 84 HIGH Repeated failed logins (> 15 in 120s), Path Traversal (../../etc/passwd), XSS. Immediate HTTP 403 Block. Temporary IP ban added to Redis cache. IP address, rule violations, payload snippet, ban TTL.
85 – 100 CRITICAL SQL Injection (UNION/SELECT), Command Injection, access to fake lures (/.env, /actuator/env). SILENT HONEYPOT TRAP ROUTING. Attacker routed into Virtual Linux Shell sandbox; Adaptive Tarpit latency injected; Canary honeytokens deployed. Command history, keystroke timing, canary exfiltration targets, STIX 2.1 intelligence bundle.

5. Architectural Risk Mitigation & Reliability Standards

Potential Failure Mode Severity Engineering Mitigation in Architecture
Redis Service Outage HIGH Fail-Open Architecture: If Redis is unreachable, the rate limiter logs a CRITICAL error and allows traffic to flow into Stage 2 rather than taking the protected site offline.
ML Engine Latency Spike MEDIUM Asynchronous Timeout Guard: ML evaluation is capped at 120ms. If processing exceeds this threshold, the deterministic rule score takes precedence immediately.
Attacker Honeypot Escape CRITICAL Pure In-Memory VFS Sandbox: Commands run in a synthetic virtual file system without spawning real OS sub-processes (no exec, os.system, or real subshells).
High Volume DoS Attacks HIGH Tiered Sliding-Window Throttling: Burst limits reject abusive IPs at the edge before deep ML feature extraction is invoked.
Ethical & Operational Safeguards
This system is built exclusively for defensive security research and authorized application shielding. The honeypot subsystem strictly monitors incoming traffic and never performs outbound lateral scanning or counter-offensive actions.
